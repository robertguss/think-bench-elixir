# Phase 1 handoff — Graph domain and event log

Worker: Opus, 2026-09-12. Scope: Phase 1 only. Phase 2 not started.

## What was built

- **Domain `ThinkBench.Graph`** (`lib/think_bench/graph.ex`), registered in
  `config :think_bench, ash_domains`. Resources under `lib/think_bench/graph/`:
  Actor, Card, Link, Region, Event, Selection, following PLAN.md's data model.
- **ash_events 0.8.1** for the event log. `Event` uses `AshEvents.EventLog` with
  `primary_key_type :integer` (bigserial) and
  `persist_actor_primary_key :actor_id, ThinkBench.Graph.Actor`. Card, Link and
  Region use `AshEvents.Events`, so every create/update/destroy action on them is
  wrapped and writes its event in the same transaction.
- **`seq`**: the event's bigserial `id`, exposed as a `seq` calculation that every
  Event read loads. It is total and matches commit order. ash_events takes a global
  `pg_advisory_xact_lock` before inserting each event (there's no multitenancy, so the
  default key is shared). Event inserts are therefore serialised: a transaction takes
  its `nextval` while holding the lock and commits before any other event insert can
  start. Tracked actions always run in a transaction, because ash_events turns them
  into manual actions, and Ash opens a transaction for manual actions whatever the
  repo's `prefer_transaction?` says. So the advisory lock really does scope to the
  write.
- **PubSub**: `ThinkBench.Graph.Changes.PublishEvent` runs on every Card, Link and
  Region write. Its `after_action` hook runs inside the transaction while the advisory
  lock is still held, and reads the newest event for the record id. That event is
  necessarily the one this action wrote. The hook puts it on the record as
  `__metadata__.event` and `__metadata__.seq`, so Phase 2 tool results can return
  `seq` without another query. An `after_transaction` hook then broadcasts
  `{:event, %Event{}}` on `ThinkBench.PubSub` topic `"graph"`, but only when the write
  succeeded. `ThinkBench.Graph.subscribe/0` and `topic/0` are helpers.
- **Code interfaces** on the domain:
  - Cards: `list_cards` (Card `:board`: `kinds`, `tags`, `include_archived`),
    `get_card` (`:by_id`, loads `created_by`, `links_out`, `links_in`), `create_card`,
    `update_card` (title, body, tags, status), `move_card(card, x, y)`, `archive_card`.
  - Links: `list_links`, `get_link`, `find_link(from, to, type)` (nil if absent),
    `link(from, to, type)`, `unlink(link_or_id)` (returns the destroyed link with
    its event metadata).
  - Regions: `list_regions`, `create_region`, `update_region`, `destroy_region`.
  - Events: `changes_since(seq)` (Event `:since`, oldest first), `latest_event`.
  - Selection: `set_selection(session_id, card_ids)` (upsert per session),
    `get_selection` (Selection `:current`: newest selection, or the one for the
    optional `session_id`; nil if none).
  - Actors: `create_actor(name, kind)` (upsert on name), `get_actor(name)`,
    `list_actors`.
  - Plain functions: `read_board(opts)` returns
    `%{cards, links, regions, latest_seq}` and `latest_seq/0`.
- **Link grammar**: an expression calculation. The six hierarchical types give
  `:hierarchy`; `cites` and any other type give `:jump`. Unique identity on
  (from, to, type). FKs to cards use `on_delete: :restrict`.
- **Migration** `priv/repo/migrations/20260913033615_phase_1_graph_domain.exs`,
  generated by `mix ash.codegen` and reviewed. The "destructive" warning is only about
  `down/0`.
- **Seeds** `priv/repo/seeds.exs`: actors `robert` (human) and `claude-code`
  (agent), plus the prototype graph: 9 cards, 8 links, 1 region, all written through
  the domain so the event log records them (21 events).
- **Tests**: 26 new tests across `test/think_bench/graph/{card,link,event,selection}_test.exs`,
  plus fixtures in `test/support/graph_fixtures.ex`.

## Verified, and how

- `mix precommit` passes: 31 tests, 0 failures, formatting and compile with warnings
  as errors are clean, and tsc passes.
- The tests cover:
  - creating, updating, moving and archiving cards (archived cards hidden unless
    asked for), kind and tag filters, `get_card` with links in and out, and
    `read_board`;
  - link uniqueness, unlink, a link to a missing card, and grammar for every known
    type plus an unknown one;
  - one event per write, with the right resource, action, actor, record id and
    increasing seq, across card create/update/move/archive, region
    create/update/destroy and link create/destroy;
  - event `data` and `changed_attributes`, and no event when a write fails
    (duplicate link, no actor, invalid move);
  - `changes_since` returning only newer events in order, and rejecting a negative
    seq;
  - PubSub broadcasts for creates and for a hard destroy (unlink), and nothing
    broadcast for a failed write;
  - selection upsert and read, and that selecting writes no events;
  - writes without a `ThinkBench.Graph.Actor` being forbidden;
  - running the seed script twice in a test giving an identical board and no new
    events.
- **Acceptance on the dev database**: after `mix ash.migrate`, I ran
  `mix run priv/repo/seeds.exs` twice. Both runs left cards 9, links 8, regions 1,
  actors 2, events 21, max seq 21. The nine titles, statuses, positions and creators
  match the script. c2 and c8 are resolved, c4 is at (80, 480) after Robert's move,
  and c9 was created by `robert`.
- **Real concurrency** (not in the suite): the sandboxed test above shares one
  connection, so it can't prove ordering. I ran a throwaway script with
  `MIX_ENV=test mix run`, sandbox in `:auto` mode, against the test database. It had
  16 concurrent writers doing 400 × (create + move) over real pool connections,
  while a separate process polled `changes_since(cursor)` in a tight loop. Result:
  800 events, 800 unique seqs, ascending. The reader saw all 800, and 0 events ever
  appeared at or behind a cursor it had already passed. 800 broadcasts were received
  and matched the log exactly. The script truncated the tables afterwards, and the
  test database was confirmed empty.

## Decisions the plan did not cover

1. **Nine cards means all five scripted turns, not three.** The prototype's first
   three turns hold only seven cards (c1–c7). The instruction said "first three turns
   (nine cards, …, one region)", and the only reading that gives nine cards and one
   region is the whole script. c8 comes from turn 4 and c9 from turn 5. c8 was a
   "proposed" card in the prototype; proposals were dropped (DESIGN.md), so it's
   seeded as a normal card. The script has 8 links, not 9.
2. **Seed idempotency keys**: cards and regions match on title, links on
   (from, to, type). Follow-up edits in the script (resolving c2 and c8, moving c4)
   are applied only to cards created in that run, so re-seeding never undoes later
   changes. Renaming a seeded card and re-seeding would create a second copy.
3. **`seq` is `Event.id`**, not a separate column. `data` holds the action input and
   `changed_attributes` holds everything else the action set (ids, defaults,
   timestamps, creator). That's ash_events' split of the plan's single `data`.
   `occurred_at`, `resource` (the module atom), `action`, `action_type` and
   `record_id` are as planned. All Event fields are public (`public_fields :all`) so
   Phase 2 can serialise them.
4. **Why not an Ash notifier for the broadcast**: ash_events 0.8.1 drops the event's
   own notification on single-record hard destroys (see the comment in
   `AshEvents.DestroyActionWrapper.destroy_result/3`), so `unlink` would never
   broadcast. The after_action lookup doesn't depend on that plumbing.
   **Caveat:** if a caller ever wraps several writes in its own outer transaction,
   the broadcasts fire when each action finishes, before the outer commit. Nothing
   does that today; the channel and MCP layers should keep one write per call.
5. **Writes require a `ThinkBench.Graph.Actor`.** Card, Link and Region have policies:
   reads always pass, and create/update/destroy need an Actor struct as the actor.
   Without one they return `Ash.Error.Forbidden` and write no event. This keeps an
   event's `actor_id` from ever being nil through the domain. Adding policies needed
   a SAT solver, so `picosat_elixir 0.2.3` was added. `created_by` is set from the
   actor, never from input.
6. **Archive is an update action** (`:archive` sets `archived_at`), so its event has
   `action: :archive, action_type: :update`. Card has no hard destroy, because links
   restrict card deletion. Link and Region have hard `:destroy`.
7. **`move_card` requires both x and y.** Card `x`/`y` default to 0. Phase 2's
   "place near the last card when x/y are absent" belongs in the tool layer or a new
   change; it isn't here.
8. **`read_board` reads `latest_seq` first**, then cards, links and regions. A write
   that lands mid-read shows up in the next `changes_since`, never skipped. Its links
   are only those whose two ends are both among the returned cards.
9. `events.actor_id` has an FK to `actors`. Actors are never deleted.
10. `bcrypt_elixir` (and its `comeonin`) are in `mix.lock` because `ash_events`
    declares `bcrypt_elixir ~> 3.0` as a dependency (`mix deps.tree`). Nothing in the
    app uses them; it's a NIF that compiles with `cc` on setup.

## Not done / notes for the reviewer

- There's no update action on Link (change a type by unlinking and linking again), no
  `kind` change on Card, and no unarchive. None is in the tool surface.
- `changes_since` has no limit or pagination. Fine at this size; Phase 2 may want a
  cap.
- Replay (`clear_records_for_replay`) isn't configured. The log is used for audit and
  change feeds only, as the plan requires.
- The concurrency script lived in the session scratchpad and is not committed. Its
  method is described above if you want to reproduce it.
- Elixir 1.20 type warnings from dependencies (ash_json_api, ash_ai) still print
  while compiling. They don't fail `--warnings-as-errors`.
